# 1P1D vs two independent TP8 instances, same 16 GPUs

Measured 2026-09-05 on four p6-b300 hosts, both arms running **at the same time** so
they cannot be separated by drift in the fabric or the host:

* **arm A -- 1P1D**: B300-1 prefill + B300-2 decode, `TRANSFER_BACKEND=mooncake`
  (`MOONCAKE_PROTOCOL=efa`), benched through the router on B300-1:8000.
* **arm B -- 2x solo**: B300-3 and B300-4, each a self-contained TP8 server, benched
  concurrently and summed.

Everything else matched: `hy4-preview-efa:latest`, MXFP8, **TP8**, MTP on
(`speculative_num_steps=3`), EP=1, `A2A_BACKEND=none`, ISL/OSL 1024/1024,
`MAX_RUNNING=128` on every server (verified from `/get_server_info`, not from the
launch env -- see `serverinfo-pd-*.json`; with MTP on SGLang silently resets this to
48 unless it is passed).

## Answer: no, 1P1D does not beat two independent instances -- and the gap widens
## with concurrency.

## What the numbers say

**1P1D saturates at ~5.0k out tok/s; two instances do not.** Going from offered 128
to 256, PD gains **+3.9%** (4884 -> 5074) while arm B gains **+52%** (5169 -> 7861).
That is the whole finding: the PD pair is already at its ceiling by offered 128.

**The ceiling is the prefill side, and its TTFT says so.** PD's median TTFT goes
2102 -> 2777 -> **24954 ms** across the ladder, a 9x jump for a 2x concurrency
increase, while arm B's stays sub-second (741 ms at offered 256). At 1024/1024 with
MTP accepting ~3.8 tokens/step, one node's worth of prefill cannot feed one node's
worth of decode: work does not split 1:1, so a 1:1 node split leaves the prefill node
as the queue and the decode node partly idle. Two independent instances each do their
own prefill and decode, so they are balanced by construction.

**PD also admits less of the offered load**: live concurrency 210.0 of 256 vs arm B's
239.8 -- so it is losing on throughput *while* serving fewer simultaneous requests,
which rules out "PD is trading concurrency for throughput".

**PD's one real win is TPOT at high load**: 19.51 ms vs 28.40 at offered 256, and it
barely degrades across the ladder (14.53 -> 18.86 -> 19.51) because the decode node
never has prefill interleaved into its steps. If a deployment is TPOT-bound and can
accept a 25 s TTFT, that is the case for PD. Nothing here is a case for PD on
throughput at this shape.

## Caveats, both stamped in the filenames

1. **`num_prompts` differs between the arms.** Arm B used `n = 4 x c` per instance,
   arm A `n = 2 x c`. Both are >= 2 rounds of the queue, so neither is warmup-dominated,
   but arm A's runs are shorter (53-103 s vs 131-135 s) and therefore noisier.
2. **Only the decode side ran `MEM_FRACTION=0.85`; every other server took SGLang's
   own default (0.899 prefill, 0.896 on each arm-B instance).** Not a choice: at 128
   slots the decode side OOMs during graph capture at the default, and the OOM
   message's suggested `expandable_segments:True` must never be used with Mooncake
   (it fails 100% of RDMA transfers). The resulting KV pools are 1.35M (decode) /
   1.49M (prefill) / 1.60M tokens (each arm-B instance) -- all far above the ~262k
   this workload needs (256 x 2048), so this is not a throughput confound. All four
   servers are otherwise identical, including `chunked_prefill_size=16384`.

## Reproduce

```bash
# arm A, on B300-1 (prefill) and B300-2 (decode), then the router on B300-1
MAX_RUNNING=128 bash 20_launch_prefill.sh                    # B300-1
MAX_RUNNING=128 MEM_FRACTION=0.85 bash 21_launch_decode.sh   # B300-2
bash 22_launch_router.sh                                     # B300-1
ENDPOINT=localhost:8000 SRV=hy4-prefill ISL=1024 OSL=1024 \
  CONCURRENCY=$C NUM_PROMPTS=$((C*2)) TAG=... bash 91_bench.sh

# arm B, on B300-3 and B300-4 independently, benched at the same wall-clock time
MAX_RUNNING=128 bash 10_launch_standalone.sh
ISL=1024 OSL=1024 CONCURRENCY=$((C/2)) NUM_PROMPTS=$((C*2)) TAG=... bash 91_bench.sh
```
